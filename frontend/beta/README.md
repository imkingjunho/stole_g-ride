# 베타·발표 준비

날짜를 기다리지 않고 준비 가능한 작업부터 진행한다. 이 폴더는 준비 자료이며 실제 베타 결과가 아니다.

## 준비된 것과 실제 검증

| 항목 | 준비 상태 | 실제 완료에 필요한 것 |
|---|---|---|
| 시연 흐름 | DEV/mock의 기능 체험 화면에 11개 독립 시나리오·체크·기록 다운로드 | 실계정·실 JWT·실제 매칭·카카오·그룹 왕복 리허설 |
| 베타 모집/진행 | 아래 운영 순서와 survey.md | 실제 참여자 모집 및 운영 |
| 설문 | survey.md, 빈 survey-responses.example.csv, 집계 명령 | 실제 응답 입력 |
| 피드백 개선 | 빈 feedback.example.csv 및 전후 기록 절차 | 실제 이슈 선정·수정·재검사 |

## 1. 목 시연 리허설

frontend에서 `npm.cmd run dev` 후 목 데이터로 로그인 → DEV · 기능 체험 → 발표 시연 리허설.

- **목 리허설 새로 시작:** 목 요청·그룹·메시지·이력·오류 주입과 수동 체크를 초기화한다. 로그인은 유지한다.
- 각 **연습** 버튼은 해당 단계의 샘플 상태를 만든다. 요청·대기·수락·정산·채팅/신고·거절·재계산·점선·오류·완료·목 갱신을 독립적으로 확인한다.
- 재계산 단계는 그룹 화면에서 **목 재계산 알림 보내기**를 누른다. 목 샘플 금액 변경이며 매칭·정산 알고리즘이 아니다. 분담액 합계와 총액은 맞추고, 변경된 내 구간별 정산은 미제공 상태로 표시한다.
- 화면 위 **시연 체크리스트로 돌아가기**로 복귀한다. 직접 확인한 항목만 체크한다.
- 체크는 현재 브라우저 탭의 sessionStorage에 저장된다. 새 탭·탭 종료 후에는 별도 기록이다.
- **리허설 기록 다운로드**는 체크 목록과 MOCK_REHEARSAL 범위만 내보낸다. 실제 서버 검증/베타 만족도로 합산하지 않는다.
- 이 도구는 DEV와 mock을 모두 만족할 때만 표시되고 real 모드에서는 상태 변경 함수도 거절한다. 운영 빌드에는 리허설 경로/도구가 노출되지 않는다.

## 2. 실제 베타를 시작할 조건

현재 main의 그룹 계약 대조는 `../INTEGRATION-REQUESTS-20261111.md`를 따른다.

1. 전용 테스트 계정 2개로 실제 로그인 → 요청 → 성사 → 그룹 조회 → 수락/거절 → 채팅 → 완료를 완주한다.
2. 그룹 응답/인가·계약 이벤트와 실제 WS 수신을 확인한다. 단순 폴링 숫자 변경만으로 WS 성공을 판정하지 않는다.
3. 운영 URL에서 /request·/waiting 직접 접속, 모바일 360px, 실제 카카오 허용 도메인·메일을 확인한다.
4. 데모/부하 계정과 실제 베타 기록을 구분하고 기록 담당자를 정한다.

서버 통합이 준비되면 일정 날짜와 관계없이 실제 베타를 시작할 수 있다. 코드·준비 문서만으로 참가자 수나 완료 항목을 올리지 않는다.

## 3. 참가자 안내와 진행

- 목표는 교내 실제 참여자 30명의 유효한 전체 만족도 응답이다. 먼저 소규모로 안내·동선을 점검하고 이후 나머지를 진행한다.
- 운영 담당자와 이용 시간/거점을 맞춰 동승 상대가 있는 조건을 준비한다. 동의한 실제 참여자의 기록만 REAL로 남긴다.
- 참여자 번호는 P001~P030 등 익명 번호로 부여한다. 이 설문 기록에는 이름·학교 이메일·연락처·토큰·비밀번호를 넣지 않는다.
- 시작 전: 동승자 매칭/요금 분담 안내 서비스이며 택시 호출·운송·결제를 중개하지 않음을 설명한다.
- 순서: 로그인/인증 → 요청 조건 입력 → 대기 상태 → 성사·요금 설명 → 수락/거절 → 채팅 → 완료 → 설문.
- 신고 기능 확인은 전용 테스트 계정으로 진행한다. 참여자가 경험하지 않은 문항은 점수를 강요하지 않고 비워 둔다.
- 막히거나 중단한 흐름도 feedback.csv에 기록한다. 실패한 참가자 기록을 조용히 버리거나 목 데이터로 대신하지 않는다.

## 4. 설문 입력과 집계

`survey-responses.example.csv`를 `survey-responses.csv`로 복사한 뒤 `survey.md`의 다섯 점수 문항을 옮긴다. 피드백도 feedback.example.csv를 feedback.csv로 복사한다. 실제 응답·피드백과 beta/results/는 Git에서 제외한다. 실제 파일명은 `survey-responses.csv`다.
CSV는 Excel 호환 UTF-8 BOM이며 헤더 순서를 유지한다. mode는 REAL 또는 MOCK,
날짜는 YYYY-MM-DD, 점수는 1~5, 미경험 문항은 빈칸이다. comment에 쉼표·줄바꿈을 넣으면 CSV 따옴표 규칙을 사용한다.

PowerShell, frontend 폴더. Copy-Item은 최초 한 번만 실행하며 기존 실제 기록 파일을 덮어쓰지 않는다:

```powershell
if (!(Test-Path beta/survey-responses.csv)) { Copy-Item beta/survey-responses.example.csv beta/survey-responses.csv }
if (!(Test-Path beta/feedback.csv)) { Copy-Item beta/feedback.example.csv beta/feedback.csv }
npm.cmd run beta:summary
npm.cmd run test:beta
```

- 실제 응답의 전체 만족도(overall_satisfaction) 유효 점수로 평균과 표본 수를 계산한다.
- MOCK 행은 제외한다. 전체 만족도 빈칸은 해당 평균/30명 목표의 분모에서 제외하고 누락 수를 표시한다.
- 항목별 평균은 각 항목의 유효 응답 수를 별도로 쓴다. 0건은 0점이 아닌 null이다.
- 실제 참여자 번호 중복, 1~5 이외 점수, 잘못된 날짜/모드/열은 오류로 중단한다.
- 목표는 유효 실제 전체 만족도 30명 이상·평균 4.0 이상이다. 출력이 목표를 충족해도 서버 통합/전체 Phase 완료를 자동 선언하지 않는다.
- 실제 응답 파일이 없으면 empty_template로 표시하고 빈 예제를 읽는다. 실제 파일이 생긴 뒤에는 기본 명령도 실제 파일을 읽는다.
- 빈 템플릿의 최초 결과는 참여자 0명·평균 null이다. 예시 점수를 실제 파일에 미리 넣지 않았다.

## 5. 피드백 상위 3건 개선

1. feedback.csv에 시나리오, 기기, 기대/실제 결과, 심각도(P0/P1/P2), 상태를 기록한다. MOCK과 REAL은 분리한다.
2. 실제 기록에서 진행 차단 정도와 발생 빈도로 상위 3건을 정한다. 표본이 없을 때 이슈/빈도를 만들지 않는다.
3. 같은 화면·같은 뷰포트·같은 재현 절차로 개선 전후 스크린샷을 남긴다. 개인 정보는 제외한다.
4. 수정·lint/build 후 같은 절차로 재검사하고 after_screenshot, retest_result, status를 갱신한다.
5. 공용 docs/beta-feedback.md 반영은 문서 담당자에게 전달한다. 내 준비 파일을 다른 사람 소유 문서에 임의로 덮어쓰지 않는다.

실제 피드백 수집·상위 3건 개선·최종 실서버 리허설이 끝나야 담당 T3 완료 체크를 갱신한다.
