## ⚠️ 이 역할의 특수성

**서준의 매칭 엔진이 이 작업 결과에 직접 의존한다.** `RouteProvider` 구현이 늦어지면
알고리즘 검증이 전부 막히므로, 8월 중 최소한 동작하는 버전을 내놓아야 한다.

지도 프론트엔드를 2차로 맡는 이유: **카카오 API 응답 구조를 가장 잘 아는 사람**이
그 데이터를 화면에 그리는 게 가장 빠르기 때문이다. 백엔드·프론트 양쪽 경험은
포트폴리오에서도 유리하다.

## Phase 1 — 카카오 API 연동 (8월) 🔥 최우선

- [ ] **T1-1. 4대 거점 좌표 데이터 구축**
  - 전남대 정문·후문·예대삼거리, 경신여고, 유스퀘어, 광주송정역
  - 위경도를 실제 확인하여 정확히 수집
  - 임승현에게 seed 데이터로 전달 (마이그레이션은 임승현이 작성)

- [ ] **T1-2. `KakaoRouteProvider` 구현** — FR-15
  - 서준이 정의한 `RouteProvider` 인터페이스 구현
  - `POST https://apis-navi.kakaomobility.com/v1/waypoints/directions`
  - 헤더: `Authorization: KakaoAK {REST_API_KEY}`, `Content-Type: application/json`
  - **응답 매핑 (PRD §6.2 — 필드명 정확히 확인할 것)**
    - `routes[0].summary.fare.taxi` → 총 요금
    - `routes[0].summary.distance` → 총 거리(m)
    - `routes[0].summary.duration` → 소요시간(초)
    - `routes[0].sections[k].distance` → **구간 거리 (정산의 핵심)**
    - `routes[0].result_code` → 0이 아니면 실패 처리
  - ⚠️ **REST 키는 백엔드 환경변수에만.** 프론트에 절대 노출 금지
  - RestClient 또는 WebClient 사용, 타임아웃 3초

- [ ] **T1-3. 실패 대응 (fallback)** — E-03
  - 3초 타임아웃, 1회 재시도
  - 실패 시 Haversine 직선거리 × 1.3 + 광주시 택시 요금표로 추정
  - 추정치임을 응답에 플래그로 표시 (프론트에서 배지 노출)

- [ ] **T1-4. Redis 캐싱**
  - 키: 출발지·경유지·목적지 좌표 조합 해시 (소수점 4자리로 반올림하여 캐시 적중률 향상)
  - TTL 10분
  - 목표: API 호출량 70% 절감. **캐시 적중률을 로그로 측정하여 기록** (포트폴리오 근거)

- [ ] **T1-5. 호출량 제어**
  - 매칭 tick당 최대 호출 수 상한 설정 (`application.yml`)
  - 일일 호출량 카운터 및 경고 로그

- [ ] **T1-6. 장소 검색 프록시** — FR-06
  - `GET /api/places/search?q=` → 카카오 로컬 키워드 검색 API 중계
  - 광주 지역으로 위치 편향(location bias) 적용
  - `GET /api/hubs` — 거점 목록 (FR-05)

## Phase 2 — 프론트엔드 지도 (10~11월)

- [ ] **T2-1. 카카오맵 SDK 초기화**
  - JS 앱 키는 `.env`에서 주입
  - ⚠️ **카카오 개발자 콘솔에서 허용 도메인 반드시 제한할 것** (JS 키는 노출이 전제)
  - `useKakaoMap` 훅으로 SDK 로딩 처리
  - ⚠️ 프론트 기본 구조는 오승원이 잡는다. 그 위에 올린다

- [ ] **T2-2. 경로 시각화** — FR-19
  - `sections[].roads[].vertexes`를 Polyline으로 렌더링
  - vertexes는 `[x, y, x, y, ...]` 1차원 배열이므로 좌표 쌍으로 변환 필요
  - 탑승/하차 지점 순서 마커 (1, 2, 3 번호 표시)
  - 경로 전체가 보이도록 `bound` 값으로 화면 맞춤

- [ ] **T2-3. 목적지 선택 지도** — FR-06
  - 검색 결과 핀 표시, 지도 클릭으로 미세 조정

- [ ] **T3-2. 누적 절감 리포트** — FR-25

  - 등하교 피크 시간대 분석 결과를 매칭 파라미터 튜닝 근거로 서준에게 제공

## 포트폴리오 정리 포인트

> "카카오모빌리티 길찾기 API를 연동하고 좌표 정규화 기반 캐싱 전략으로
> 호출량 70% 절감. API 장애 시 Haversine 기반 fallback으로 가용성 확보.
> 동일 데이터를 프론트엔드 지도 컴포넌트로 시각화하여 백엔드-프론트 전 구간을 담당."

- 캐시 키를 좌표 소수점 4자리로 반올림한 이유 (미세한 좌표 차이로 캐시가 안 맞는 문제)
- fallback 보정계수 1.3의 근거

이 두 가지는 "그냥 API 붙였다"와 "설계했다"를 가르는 지점이다. 수치와 함께 기록해 둘 것.
