## ⚠️ 이 역할의 특수성

프로젝트에서 **기술적으로 가장 어렵고, 가장 어필되는 영역**이다.
동시에 다른 사람의 결과물(카카오 API, 대기열)에 가장 많이 의존한다.
따라서 **남을 기다리지 않기 위해 인터페이스와 Stub을 먼저 만들고 알고리즘부터 완성한다.**

**작업 근거는 반드시 PRD §5다.** 알고리즘을 임의로 단순화하지 않는다.
특히 §5.2 구간 분할 정산은 이 프로젝트의 핵심 차별점이므로 단순 1/N으로 바꾸지 않는다.

## Phase 1 — 설계 및 오프라인 프로토타입 (8~9월)

- [ ] **T1-1. 포트 인터페이스 정의** 🔥 최우선
  - `matching/port/RouteProvider` — 경로·요금 조회 (송준호가 구현)
  - `RouteResult` DTO — `totalFare`, `totalDistance`, `sections[]{distance}`
  - **이 인터페이스를 먼저 확정해야 송준호와 병렬 작업이 가능하다.** 8월 1주차에 끝낼 것
  - `FixedRouteProvider` — 고정값 반환 테스트 구현체

- [ ] **T1-2. 도메인 모델**
  - `MatchGroup`, `MatchMember` 엔티티 (PRD §7)
  - `MatchCandidate` — 평가 대상 조합을 표현하는 값 객체

- [ ] **T1-3. 구간 분할 정산 구현** — FR-16 (PRD §5.2)
  - `FareCalculator.calculate(RouteResult, List<Member>) → Map<userId, share>`
  - 구간 요금 `F_k = F × (d_k / D)`, 인당 `F_k / p_k`
  - 100원 단위 올림, 잔액은 최대 분담자에게서 차감
  - **✅ 필수 테스트: `Σ share_i == 총 요금` (오차 1원 이내)**
  - PRD §5.2의 3인 예시(15,000원 / A=1,500 B=3,750 C=9,750)를 테스트 케이스로 그대로 포함
  - **이 작업은 외부 의존성이 없으므로 8월에 바로 시작 가능하다**

- [ ] **T1-4. 하드 필터** — PRD §5.1 Step 1
  - 거점 동일 / 시간창 5분 / 성별 옵션 호환 / 목적지 3km / 정원 4명
  - 순수 함수로 구현하여 단위 테스트 용이하게

- [ ] **T1-5. 목적지 클러스터링** — PRD §5.1 Step 2
  - Haversine 거리 함수
  - 단일 연결 계층적 클러스터링, 임계 3km
  - 버킷당 최대 20건 제한 (조합 폭발 방지)

## Phase 2 — 매칭 엔진 본구현 (10월)

- [ ] **T2-1. 조합 평가** — PRD §5.1 Step 3
  - 크기 2~4 조합 생성
  - `RouteProvider` 호출 → 우회율 계산
  - 수용 조건: `∀i detour_ratio_i ≤ max_detour_i` AND `∀i saving_i > 0`
  - ⚠️ API 호출 비용이 크므로 조합 수를 사전에 제한한다

- [ ] **T2-2. 점수화 및 그리디 선택** — PRD §5.1 Step 4
  - `score = w₁·Σsaving − w₂·avg(detour)·10000 − w₃·max(wait)`
  - 가중치는 `application.yml`에서 주입 (튜닝 가능하게)
  - 이미 배정된 사용자 제외

- [ ] **T2-3. `MatchingService.executeTick()`** — FR-11
  - 대기열 조회 → 필터 → 클러스터링 → 평가 → 그룹 확정
  - 이승민의 스케줄러가 호출한다
  - 실행 시간 측정 로그 (목표 2초 이내)

- [ ] **T2-4. 그룹 확정 및 수락 처리** — FR-12, FR-13
  - `POST /api/groups/{id}/accept`, `/reject`
  - 60초 내 전원 수락해야 성사, 1명이라도 거절 시 해체 후 재대기열
  - 낙관적 락으로 중복 배정 방지 (E-02)

- [ ] **T2-5. 그룹 해체 및 재계산** — FR-14, E-01
  - 성사 후 1명 취소 시: 2명 이상이면 경로·요금 재계산 후 재동의 요청, 1명이면 해체

- [ ] **T2-6. 우회 보상 할인** — FR-18 (PRD §5.3)
  - `detour_ratio > 0.15`인 사용자에게 할인, 총액 F 보존
  - **✅ 필수 테스트: 할인 적용 후에도 `Σ share == F`**

- [ ] **T2-7. 그룹 상세 조회 API** — FR-17
  - `GET /api/groups/{id}` — 경로, 탑승/하차 순서, 분담액, 절감액

## Phase 3 — 검증 및 문서 (11~12월)

- [ ] **T3-1. 시뮬레이션 데이터 생성** — 가상 동승 시나리오 1,000건으로 알고리즘 안정성 검증

## 포트폴리오 정리 포인트

> "T-Share·ExMAS 논문을 참고해 거점 기반 동승 매칭 휴리스틱을 설계하고,
> 카카오모빌리티 API의 구간별 거리를 활용한 구간 분할 정산 모델을 구현.
> 단순 1/N 대비 먼저 하차하는 승객의 부담을 평균 XX% 감소시킴."

- 왜 일반 DARP가 아니라 그리디 휴리스틱인지 (출발지가 소수 거점으로 고정 → 탐색 공간 축소)
- 왜 단순 1/N이 아니라 구간 분할인지 (공정성 논증)

이 두 가지는 반드시 설명할 수 있어야 한다. 발표와 면접에서 가장 많이 나온다.
