# 서준 — 파트 ② 매칭·정산·통계 (+ PM)

> 이 파일은 AI 코딩 어시스턴트가 읽는 작업 지시서다. 완료한 항목은 `[x]`로 바꾼다. AI는 **가장 위의 미완료 항목**부터 진행한다.
> 근거 문서는 `docs/PRD.md`. 특히 **§5(알고리즘 — 임의로 단순화 금지)**, §12.3-②, §14(계약)를 따른다.
> Phase 1 이후 항목은 이승민의 "Phase 0 끝" 공지 뒤에 시작한다.

## 내 파트 한 줄

**매칭 엔진(§5.1) → 구간 분할 정산(§5.2) → 그룹 API → 이력·통계**. 이 프로젝트에서 기술적으로 가장 어렵고 가장 어필되는 영역. 남을 기다리지 않도록 계약(포트)과 스텁이 먼저 깔려 있다 — **스텁 위에서 알고리즘을 먼저 완성한다.** PM으로 주간 통합 점검을 진행한다.

## 내 폴더 (여기만 수정한다)

```
backend/src/main/java/com/gachiga/
├── matching/     매칭 엔진, tick 스케줄러, MatchGroup·MatchMember, 그룹 API, MatchHistoryPort 구현
├── fare/         구간 분할 정산, 우회 보상 할인
└── stats/        이력·통계 API
backend/src/main/resources/domain/matching.yml     (가중치 w1~w3, tick 주기, 버킷 상한 등)
backend/src/test/java/com/gachiga/{matching,fare,stats}/
```

## 담당 FR

**FR-11**(배치 매칭), **FR-12**(그룹 확정), FR-13(수락·거절, P1), **FR-14**(해체), **FR-16**(구간 분할 정산), **FR-17**(절감액 계산), FR-18(우회 할인, P1), FR-24(이력, P1), FR-25·26(통계, P2), E-01, E-02(사용 측), E-06, E-07

## 계약 (PRD §14)

| 내가 **구현**하는 것 | 내가 **쓰는** 것 |
|---|---|
| `MatchHistoryPort` (임승현 realtime·user가 사용) | `RideRequestPort` (이승민) — 대기열 읽기, `tryMarkMatched`, 상태 변경 |
| 이벤트 발행: `GroupProposed / Confirmed / Recalculated / Dissolved / Completed` | `RouteProvider`, `HubPort` (송준호) — 조합 평가용 경로·요금, 출발 좌표 |
| | `UserPort` (임승현) — 성별 필터 |

**중요:** `ride`·`route`·`user` 패키지의 클래스를 직접 import 하지 않는다. ArchUnit이 빌드를 실패시킨다. 필요한 정보가 계약에 없으면 `[계약 변경 요청]`을 단톡방에.

## Phase 1 (9/28 ~ 10/25) — P0

- [ ] **T1-1. 정산기** — `fare/FareCalculator.calculate(RouteResult route, List<Rider> riders) → Map<userId, Share>` (FR-16, FR-17)
  - 구간 요금 `F_k = F × d_k / D`, 인당 `F_k / p_k`, 사용자 분담 = 탑승 구간 합
  - 100원 단위 **올림**, 초과 잔액은 최대 분담자에서 차감
  - `saving_i = soloFare_i − share_i`, `detour_ratio_i = (sharedDistance_i − soloDistance_i) / soloDistance_i`
  - E-07: 목적지 100m 이내 → 단일 목적지·균등 분할
  - **필수 테스트:** `Σ share == totalFare`(오차 0), PRD §5.2 3인 예시 그대로, 2인·4인, 무작위 100케이스 프로퍼티 테스트. 금액은 `int`, `double` 금지
- [ ] **T1-2. 도메인 모델** — `MatchGroup`, `MatchMember` 엔티티 (PRD §7). `userId`·`requestId`·`hubId`는 `Long`. `MatchCandidate` 값 객체
- [ ] **T1-3. 하드 필터** — §5.1 Step 1 순수 함수 `HardFilter.compatible(a, b)`: 거점 동일, 시간창 5분, 성별 옵션(E-06, `UserPort`로 성별 조회 후 주입), 목적지 3km, 정원 4
- [ ] **T1-4. 클러스터링** — §5.1 Step 2. 위경도→미터 근사 투영, 단일 연결 계층 클러스터링 임계 3km, 버킷당 최대 20건. 크기 2~4 조합 생성기
- [ ] **T1-5. 조합 평가** — §5.1 Step 3. 조합마다 `RouteProvider` 1회(하차 순서는 거점에서 가까운 목적지부터 — 거리순 휴리스틱), 정산기로 share·saving·detour 계산, 수용 조건 검사. 호출 수 상한은 `matching.yml`
- [ ] **T1-6. 점수화·그리디 선택** — §5.1 Step 4. 가중치는 `matching.yml`에서 주입(`gachiga.matching.weights.w1/w2/w3`)
- [ ] **T1-7. `MatchingEngine.executeTick()` + 스케줄러** — 30초 `@Scheduled`. `RideRequestPort.findWaiting()` → 필터 → 클러스터 → 평가 → 선택 → 그룹 저장. **`tryMarkMatched`가 false인 요청이 있으면 그 그룹은 폐기**(E-02). 실행 시간 로그(목표 2초/100건)

## 이 파트만으로 보여줄 수 있는 것

`EstimatedRouteProvider`(스텁)와 인메모리 요청으로 **정산 단위 테스트·매칭 시뮬레이션 결과**를 보여줄 수 있다. 스텁이 `estimated=true`를 주므로 화면엔 "추정치"가 뜨지만 알고리즘 검증은 완전히 가능하다.

## 포트폴리오 포인트

> "T-Share·ExMAS 논문을 참고해 거점 기반 동승 매칭 휴리스틱을 설계하고, 카카오모빌리티 API의 구간별 거리를 활용한 구간 분할 정산 모델을 구현. 단순 1/N 대비 먼저 하차하는 승객의 부담을 평균 XX% 감소시킴. 시뮬레이션 1,000건으로 파라미터를 튜닝해 성사율 XX% 달성."

- 왜 일반 DARP가 아니라 그리디 휴리스틱인가 (출발지가 소수 거점 → 탐색 공간 축소)
- 왜 1/N이 아니라 구간 분할인가 (공정성 논증)
- 낙관적 락 실패 시 그룹을 폐기하는 이유 (E-02)

이 세 가지는 발표와 면접에서 반드시 나온다.
