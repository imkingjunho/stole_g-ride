# 이승민 — 백엔드 코어 리드

> 이 파일은 AI 코딩 어시스턴트가 읽는 작업 지시서입니다.
> 완료한 항목은 `[x]`로 바꿔 주세요. AI는 **가장 위의 미완료 항목**부터 진행합니다.
> ⛔ **코드를 쓰기 전에 `docs/WORK-ORDER.md`에서 이 작업의 선행 항목을 확인하세요.** 선행이 안 끝났으면 AI가 멈추고 누가 먼저 해야 하는지 알려줍니다.

## 담당 범위

| 구분 | 내용 |
|---|---|
| 패키지 | `backend/.../ride/`, `backend/.../common/`, `backend/.../config/` |
| 담당 FR | FR-08, FR-09, FR-10 |
| 1차 도메인 | 서버 기반 구조, 매칭 요청, 대기열, 스케줄러 |
| 2차 도메인 | 전체 API 통합, 성능 튜닝 |

## ⚠️ 이 역할의 특수성

`common`과 `config`는 **팀 전원이 의존하는 기반**이다. 여기가 늦어지면 4명이 전부 대기한다.
8월 1~2주차 작업은 **크리티컬 패스**이므로 다른 무엇보다 먼저 끝낸다.
또한 이 패키지들은 확정 후 함부로 바꾸면 안 된다. 변경 시 반드시 팀에 공지한다.

## Phase 1 — 기반 구조 (8월) 🔥 최우선

- [ ] **T1-1. 프로젝트 초기 설정**
  - Spring Boot 3.2 + Java 17 프로젝트 생성 (Gradle)
  - 의존성: Web, Data JPA, Validation, Security, WebSocket, Redis, MySQL Driver, Lombok, springdoc-openapi
  - `application-local.yml` / `application-prod.yml` 프로파일 분리
  - 완료 기준: `./gradlew bootRun`으로 서버가 뜬다

- [ ] **T1-2. 공통 응답 표준** (`common/response/`)
  - `ApiResponse<T>` — `{ success, data, error }` 구조 (PRD §8)
  - `ApiError` — `{ code, message }`
  - 성공/실패 정적 팩토리 메서드
  - 완료 기준: 팀에 공유하고 승인받는다. **이후 변경 금지**

- [ ] **T1-3. 예외 처리 체계** (`common/exception/`)
  - `BusinessException` 기반 클래스
  - `ErrorCode` enum — `MATCH_EXPIRED`, `ALREADY_IN_QUEUE`, `INVALID_TOKEN`, `ROUTE_API_FAILED` 등
  - `@RestControllerAdvice`로 전역 처리 (Validation 예외 포함)
  - 완료 기준: 예외 발생 시 항상 `ApiResponse` 형태로 응답한다

- [ ] **T1-4. Docker Compose 환경**
  - MySQL 8.0 + Redis 7 컨테이너
  - `.env.example` 작성 (**실제 키 값 금지, placeholder만**)
  - 완료 기준: 팀원이 `docker compose up -d` 한 번으로 개발 환경을 갖춘다

- [ ] **T1-5. Swagger 설정**
  - springdoc-openapi 연결, `/swagger-ui.html` 접근 확인
  - JWT 인증 헤더 입력 UI 설정

## Phase 2 — 매칭 요청 도메인 (9월)

- [ ] **T2-1. 엔티티 및 리포지토리** (`ride/`)
  - `RideRequest` 엔티티 — PRD §7 스키마 그대로
  - `status` enum: `WAITING`, `MATCHED`, `CONFIRMED`, `CANCELLED`, `EXPIRED`, `COMPLETED`
  - `@Version` 낙관적 락 필드 포함 (엣지 케이스 E-02 대응)
  - ⚠️ 마이그레이션 SQL은 임승현에게 요청. 직접 작성하지 않는다

- [ ] **T2-2. 매칭 요청 생성 API** — FR-08
  - `POST /api/requests`
  - 검증: 진행 중 요청 1건 제한, 출발지-목적지 최소 500m (E-08)
  - `solo_distance`, `solo_fare`를 `RouteProvider`로 조회해 캐시
  - ⚠️ `RouteProvider`는 송준호 담당. 인터페이스만 참조하고 Stub으로 개발

- [ ] **T2-3. 요청 취소 / 조회 API** — FR-08
  - `DELETE /api/requests/{id}` — 본인 요청만, 대기열 즉시 제거
  - `GET /api/requests/me`

- [ ] **T2-4. Redis 대기열**
  - 거점별 Sorted Set (score = 희망 출발 시각)
  - 등록·제거·조회 연산
  - 완료 기준: DB와 Redis 상태가 항상 일치한다 (트랜잭션 경계 주의)

- [ ] **T2-5. 만료 스케줄러** — FR-10
  - 30초 주기로 `expires_at` 경과 요청을 `EXPIRED` 처리
  - 만료 30초 전부터 신규 배정 중단 플래그 (E-04)

## Phase 3 — 매칭 엔진 연동 (10월)

- [ ] **T3-1. 매칭 tick 스케줄러** — FR-11
  - 30초 주기로 `MatchingService.executeTick()` 호출
  - ⚠️ `MatchingService`는 서준 담당. 인터페이스 호출만 담당한다
  - 실행 시간 로깅 (목표: 대기 100건 기준 2초 이내)

- [ ] **T3-2. 대기 상태 실시간 알림** — FR-09
  - WebSocket `/ws/queue` 엔드포인트
  - 남은 대기시간, 현재 후보 인원 수 push
  - ⚠️ STOMP 설정은 임승현의 chat과 공유. 설정 충돌 없도록 협의

## Phase 4 — 통합 및 성능 (11~12월)

- [ ] **T4-1. 전체 API 통합 점검** — 모든 엔드포인트가 `docs/api-spec.yaml`과 일치하는지 대조
- [ ] **T4-2. N+1 쿼리 제거** — `@EntityGraph` 또는 fetch join 적용, 쿼리 로그 확인
- [ ] **T4-3. k6 부하 테스트** — 동시 200명 시나리오, 목표 P95 < 500ms
- [ ] **T4-4. 성능 개선 결과 문서화** — `docs/performance.md`에 개선 전후 수치 기록 (포트폴리오 자료)
