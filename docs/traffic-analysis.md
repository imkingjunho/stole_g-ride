# 광주 시간대별 교통 분석 기준

> T3-4 결과물. 공개 데이터가 확보되면 아래 기준으로 분석하고, 매칭 파라미터 튜닝의 근거로 사용한다.

## 1. 목적

전남대 주변 6개 거점의 등하교·귀향 피크 시간대를 확인하여 다음 매칭 파라미터를 조정한다.

- 매칭 tick 주기와 대기시간 선택지
- 거점별 매칭 우선순위
- 허용 우회율과 후보 조합 평가 가중치
- 데이터가 부족한 시간대의 재시도·예약 매칭 필요성

분석 결과는 실제 교통량과 서비스 내부 매칭 로그를 구분한다. 교통량은 매칭 가능성의 보조 지표이며, 성사율을 직접 의미하지 않는다.

현재 저장소에는 원천 데이터와 포털 인증키가 없다. 따라서 수치와 파일을 확보하기 전에는 특정 시간대의 교통량을 단정하지 않는다. 데이터 수집 시 원본 파일, 다운로드 일시, 제공기관, 공간 단위를 함께 보관한다.

## 4. 분석 단위와 전처리

1. 기간은 가능한 최근 4주 이상으로 고정하고, 평일과 주말을 분리한다.
2. 시간 단위는 30분으로 통일한다. 원천 데이터가 시간 단위이면 그대로 사용하고, 더 짧은 단위이면 30분 합계 또는 평균으로 집계한다.
3. 좌표 데이터는 허브 반경 500m를 기본 공간 범위로 사용한다. 원천 데이터가 격자 단위이면 허브를 포함하는 격자를 우선 사용하고, 경계 격자는 별도 표기한다.
4. 결측값은 0으로 대체하지 않는다. 결측 구간은 제외하고 유효 관측 수를 함께 기록한다.
5. 동일 지표의 날짜별 값은 평균과 중앙값을 모두 산출하여 특정 행사일·사고일의 영향을 확인한다.
6. 시간대별 비교는 각 시간대의 `관측값 / 같은 요일의 일중 중앙값`인 상대 지수도 함께 사용한다.

## 5. 산출 지표

### 외부 교통 지표

- `traffic_index`: 시간대 교통량 / 해당 요일 일중 중앙값
- `pedestrian_index`: 유동인구 또는 승하차 수 / 해당 요일 일중 중앙값
- `taxi_activity_index`: 택시 운행 건수 / 해당 요일 일중 중앙값
- `valid_observations`: 집계에 사용된 유효 관측 수

### 서비스 내부 검증 지표

- `request_count`: 해당 허브·시간대 매칭 요청 수
- `matched_group_count`: 성사 그룹 수
- `match_rate`: 성사 그룹 수 / 전체 요청 수
- `median_wait_seconds`: 요청 생성부터 그룹 확정까지의 중앙 대기시간
- `route_api_call_count`: 경로 API 호출 수

외부 지표만으로 `match_rate`를 계산하지 않는다. 내부 서비스 로그가 쌓인 이후 외부 지표와 상관관계를 비교한다.

## 6. 1차 분석 시간대

원천 데이터 수집 후 아래 구간을 우선 비교한다. 이는 분석 구간 정의이며, 실제 피크 여부를 미리 확정한 결과가 아니다.

| 구분 | 시간대 | 우선 거점 | 확인할 목적 |
|---|---|---|---|
| 오전 등교 | 07:00–10:00 | 후문·정문·예대 삼거리 | 학교 방향 수요 집중 여부 |
| 점심·수업 교대 | 11:00–14:00 | 후문·정문 | 수요가 낮은 시간대의 기본값 |
| 오후 하교 | 16:00–19:00 | 후문·정문·예대 삼거리 | 목적지 분산과 대기시간 |
| 저녁 이동 | 19:00–22:00 | 경신여고·유스퀘어 | 생활권 방향 수요 |
| 귀향 수요 | 금요일 16:00–20:00 | 유스퀘어·광주송정역 | 역·터미널 방향 수요 |
| 심야 | 22:00–01:00 | 유스퀘어·전남대 | 데이터 부족 및 안전 수요 |

## 7. 매칭 파라미터 적용 규칙

실제 데이터가 확보된 뒤 시간대별 교통 지수와 내부 요청량을 함께 보고 다음 규칙으로 튜닝한다.

1. `traffic_index`가 높고 `request_count`도 높은 구간은 기본 30초 tick을 유지하고, 후보 조합 평가를 우선한다.
2. `traffic_index`가 높지만 `request_count`가 낮은 구간은 교통량만으로 대기시간을 늘리지 않는다. 수요 부족으로 판단되면 예약 매칭 또는 재시도 안내를 검토한다.
3. `request_count`가 높고 `match_rate`가 낮으면 우회율 제한을 완화하기 전에 동일 출발 거점·목적지 권역의 분포를 먼저 확인한다.
4. 특정 거점의 `median_wait_seconds`가 목표 300초를 넘으면 해당 거점·시간대의 허용 대기시간 선택지를 별도로 검토한다.
5. 파라미터 변경 전후 최소 1주를 비교하고, 요청 수가 적은 구간은 결론을 보류한다.

### 변경 이력 기록 형식

| 적용일 | 거점·시간대 | 변경 파라미터 | 변경 전 | 변경 후 | 근거 | 검증 기간 |
|---|---|---|---:|---:|---|---|
| YYYY-MM-DD | 예: 전남대 후문 07:00–10:00 | 예: 최대 우회율 | 20% | 30% | 내부 요청 00건, 성사율 00% | 7일 |

## 8. 다음 수집 작업

- 광주 빅데이터 통합플랫폼에서 교통량, 유동인구, 대중교통 승하차 데이터의 다운로드 형식과 공간 단위를 확인한다.
- TIMS에서 광주 지역 택시 운행·노드링크 데이터 제공 범위와 이용 조건을 확인한다.
- 원천 데이터 파일을 별도 저장소 또는 공유 위치에 보관하고, 이 문서의 출처 표를 갱신한다.
- 서비스 출시 후 `request_count`, `matched_group_count`, `median_wait_seconds`를 집계할 `stats` 이벤트 항목을 백엔드 담당자와 합의한다.
